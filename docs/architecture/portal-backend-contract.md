# ClinicFlow Portal Backend Contract

This document defines the security and data invariants that every production
backend adapter must preserve. `WorkspaceDataProvider` selects an in-memory
adapter only when `VITE_DEMO_MODE=true`; configured non-demo deployments use
`SupabaseWorkspaceRepository` and hospital-filtered Realtime subscriptions.
Demo tests prove interface behavior, while database and production-backed tests
must prove the same behavior at the authorization boundary.

## Portal identities

Every authenticated session must be issued by the server and contain:

- `userId`: immutable user identifier
- `role`: `super_admin`, `clinic_admin`, `doctor`, or `receptionist`
- `clinicId`: immutable tenant identifier for clinic-bound users
- short-lived session expiry and a server-side revocation mechanism

The client may use these values to shape the interface, but the API must repeat
authorization for every request. A hidden button is never an authorization
boundary.

## Tenant isolation

Every clinical and operational row must carry `clinicId`. Database policies and
queries must reject cross-clinic reads and writes by default.

- Platform administrators manage clinics, subscriptions, and platform users.
  They do not receive patient, prescription, lab, or billing records by default.
- Clinic administrators operate only inside their assigned clinic.
- Doctors receive only patients, appointments, prescriptions, and lab reports
  assigned to them or explicitly shared with them.
- Receptionists can manage registration, scheduling, billing, and lab uploads,
  but cannot create or edit prescriptions.

Use database row-level security where available. Application filters alone are
not sufficient.

## Command rules

Commands must be validated server-side using the same permission names defined
in `src/lib/access-control.ts`.

- IDs are generated by the server.
- Foreign keys must belong to the same `clinicId`.
- Prescription signer identity comes from the authenticated session, never a
  request-body doctor ID.
- Financial status changes use a transaction and retain the previous value.
- Retried create requests require idempotency keys.
- Concurrent updates require a version or `updatedAt` precondition.

## Audit requirements

Every create, update, export, login, permission change, and record access must
write an append-only audit event containing:

- actor user and role
- clinic
- action and entity identifiers
- timestamp in UTC
- request/correlation ID
- outcome
- source IP and user agent where legally permitted

Audit records must not be editable through normal application APIs. Export
events must include the requested scope and filters.

## Medical-data safeguards

Before real hospital use, the backend must provide:

- encryption in transit and at rest
- managed secrets and key rotation
- database backups with tested restoration
- disaster-recovery targets and monitoring
- rate limiting, lockout, MFA, and session revocation
- malware scanning for uploads
- signed, expiring file URLs
- consent and retention controls
- structured logging without patient data
- jurisdiction-specific compliance and a completed security assessment

Marketing claims such as HIPAA, GDPR, or ISO certification must not be presented
as achieved until they have been independently verified.

## Adapter verification

Keep route permissions and tenant-scoped selectors as defense in depth. Every
Supabase command must remain transactional, idempotent where retried, protected
by row-level security, and covered by denied-access tests. The UI must handle
loading, validation, conflict, offline, unauthorized, and retry states for every
command before production rollout.
